# План прохождения тест-кейсов

Документ для продуктового чекпоинта: как решение выглядит **снаружи** (вход → выход) на типовых проверках.  
Ниже зафиксирован контракт и типы сценариев. Когда кейсы появятся, для каждого добавим строку в таблицу «Открытые кейсы» и прогоним в прототипе / пайплайне.

Связанные артефакты: [требования](requirements.md) (§1.1 контракт, шкала уверенности), [sequence](sequence.md), [прототип](frontend/).

---

## 1. Внешний контракт (для любого кейса)

### Запрос

| Поле | Обязательность | Лимит | Смысл |
| --- | --- | --- | --- |
| `title` | да | ≤ 300 | Название товара |
| `description` | да | ≤ 6000 | Описание |
| `seller_attrs` | нет | — | Сырые атрибуты, которые селлер уже указал |

Изображения не используются.

### Ответ

Список обязательных атрибутов категории:

```text
{ attribute, value | null, confidence ∈ [0, 1], needs_review }
```

Правила:
- значение в **каноне** каталога (если удалось сопоставить со справочником);
- значение опирается на текст карточки — **без выдумок**;
- `confidence < 0,85` или пустой `value` → `needs_review = true` (подсветка, ручная проверка);
- `confidence ≥ 0,85` и есть значение → можно считать надёжным, пока селлер не правил.

### Обязательные поля (из задания)

| Категория | Атрибуты |
| --- | --- |
| Смартфон | бренд, модель, объём памяти, диагональ экрана, ёмкость батареи, цвет |
| Ноутбук | бренд, процессор, объём ОЗУ, накопитель, диагональ, цвет |

Точный перечень на прогонах — по датасету / формулировке кейсодателя.

### Как видит пользователь (UI)

1. Ввод названия и описания → «Подготовить карточку»  
2. Ожидание: «Изучаю информацию и готовлю карточку»  
3. Результат: атрибут / значение / уверенность → правка → «Новая карточка»

## 2. Типы сценариев (пока без официальных ID)

Пока кейсов нет, планируем прохождение по **типам**. На каждый тип уже есть или будет демо во входе прототипа.

| Тип | Что проверяем | Вход (идея) | Ожидаемый выход снаружи |
| --- | --- | --- | --- |
| A. Богатая карточка смартфона | Извлечение явных характеристик | Полные title + description (бренд, память, диагональ, батарея, цвет) | Заполнены обязательные поля смартфона; на явных фактах высокая уверенность (≥ 0,85) |
| B. Богатая карточка ноутбука | Другой набор обязательных полей | Полные title + description (бренд, CPU, ОЗУ, SSD, диагональ, цвет) | Заполнены обязательные поля ноутбука; явные факты — высокая уверенность |
| C. Слабый / размытый текст | Нет выдумок при бедном сигнале | Мало конкретики («телефон хороший», «памяти много») | Пустые или low-confidence поля; селлер дозаполняет вручную; не подставляем значения «с похожего SKU» |
| D. Синонимы и разный язык | Нормализация к канону | Цвет/единицы в вариантах («алый», `red`, `256gb`) | В ответе канон справочника (напр. «красный», «256 ГБ»), не сырая цитата как финал |
| E. Нет сигнала по полю | Отказ мэппинга / пустой слот | В тексте нет, например, цвета или батареи | `value = null`, `needs_review = true` для этого атрибута; остальные поля из текста могут быть заполнены |
| F. Соблюдение ограничений кейса | Только текст, эталон, анти-галлюцинации | Любой валидный кейс | Нет опоры на фото; нет копирования атрибутов с других товаров каталога |

### Демо в текущем прототипе (заготовка под типы A–C)

| Демо-кнопка | Тип | Название (кратко) |
| --- | --- | --- |
| Смартфон | A | Samsung Galaxy S24 256 ГБ чёрный |
| Ноутбук | B | ASUS VivoBook 16, i5, 16 ГБ, SSD 512 ГБ |
| Слабое описание | C | «Телефон хороший новый» + размытое описание |

## 3. Открытые кейсы организаторов

*Раздел заполняется после выдачи набора.*

| ID кейса | Тип (A–F) | Вход (title / description) | Ожидаемый выход (атрибуты) | Статус прогона | Комментарий |
| --- | --- | --- | --- | --- | --- |
| — | — | ожидает выдачи | — | не начат | — |

**Порядок работы после выдачи кейсов:**
1. Разнести каждый кейс по типу A–F и вписать в таблицу выше.
2. Для каждого зафиксировать ожидаемую таблицу атрибутов (канон + уверенность / needs_review).
3. Прогнать через API / UI прототипа; отметить статус (ok / частично / fail).
4. Расхождения занести в комментарий и в петлю улучшения (правка правил / разметка) — см. конец [requirements.md](requirements.md).

Ежедневные прогоны по расписанию этапа разработки (ориентир организаторов: 16.10–23.10) — по мере появления открытых кейсов и лидерборда.

## 4. Критерии «кейс пройден»

Кейс считаем пройденным снаружи, если одновременно:
1. Ответ содержит все обязательные слоты категории (значение или явный пустой + review).
2. Нет значений, которых нет в тексте входа (выдумки).
3. Канон соблюдён там, где значение найдено и есть в эталоне.
4. Поля с `confidence < 0,85` или без значения помечены как требующие проверки.
5. UI/API отражают один и тот же контракт.
