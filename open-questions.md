# Открытые вопросы

## 1. Есть ли требования от маркетплейса к формату названий товаров?

**Статус:** нужно уточнить у заказчика (М.Видео).

В материалах кейса единого шаблона названия нет: заголовок — свободный текст селлера. После ответа заказчика станет понятно, нужны ли отдельные правила нейминга (порядок «тип → бренд → модель…», запрет запятых и т.п.) или достаточно текущего подхода «извлекаем атрибуты из любого title».

---

## 2. Есть ли требования от маркетплейса к формату заполнения полей атрибутов? (Например для диагонали: `16 дюйма`)

**Статус:** нужно уточнить у заказчика (М.Видео).

В задании зафиксирован принцип канона и нормализации (например «алый» / «red» → единое значение), но точный перечень допустимых форматов и единиц по каждому атрибуту должен прийти со справочником/эталоном. После ответа заказчика зафиксируем правила мэппинга в требованиях и в эталоне категории.

## 3. Ограничение на количество символов в заголовке?

**Решение в прототипе:** **≤ 300 символов** (`requirements.md`, `plan-keysov.md`).

**На чём основали:**

| Источник | Вывод |
| --- | --- |
| Датасет `cu_ws/sku_desc.parquet` | Медиана title ≈ 43; p95 ≈ 88; p99 ≈ 124; max ≈ 288. Значений длиннее 300 нет. Лимит 300 покрывает весь наблюдаемый каталог с запасом. |
| Практика Ozon / Wildberries | У маркетплейсов название обычно короче описания: часто ориентиры порядка десятков–первых сотен символов (у WB исторически жёсткие короткие лимиты на «название для карточки», у Ozon — порядка до ~200–255 в зависимости от типа контента). Берём верхнюю практичную границу **300**, чтобы не резать реальные title из датасета М.Видео и не расходиться с привычкой селлеров других площадок. |

В UI: счётчик `N / 300`, ввод сверх лимита недоступен.

## 4. Ограничение на количество символов в описании?

**Решение в прототипе:** **≤ 6000 символов** (`requirements.md`, `plan-keysov.md`).

**На чём основали:**

| Источник | Вывод |
| --- | --- |
| Датасет `cu_ws/sku_desc.parquet` | Медиана description ≈ 630; p95 ≈ 1634; p99 ≈ 2737. Доля описаний > 6000 ≈ 0,08%; единичные выбросы до ~27k. Лимит 6000 закрывает почти весь корпус и отсекает аномально длинные вставки. |
| Практика Ozon / Wildberries | Описание на маркетплейсах существенно длиннее названия: тысячи символов (часто ориентиры 4000–6000+ для текстового/rich-описания). **6000** — рабочий компромисс: хватает для типичных карточек электроники и совпадает с привычными лимитами площадок, не раздувая вход пайплайна. |

В UI: счётчик `N / 6000`, ввод сверх лимита недоступен.

*Оговорка:* точные лимиты М.Видео при появлении от заказчика можно подтянуть без смены контракта API — только константы валидации.

## 5. Как быть, если у бренда цвет называется «ржавая осень», а по факту это оранжевый или коричневый?

**Решение (продуктовая политика):**

Это конфликт **маркетингового имени** и **фасетного канона фильтра**. Это разные сущности.

| Уровень | Что храним | Зачем |
| --- | --- | --- |
| A. Как в тексте / у бренда | `ржавая осень` | Карточка правдива для покупателя |
| B. Канон фильтра каталога | `оранжевый` / `коричневый` **только если есть правило в эталоне** | Поиск и фильтры |

Правила:

1. Источник истины — **справочник М.Видео**, не «наш вкус». Есть мэппинг `ржавая осень → оранжевый` — пишем канон фильтра. Нет мэппинга — **не угадываем** «похоже на коричневый» (см. ограничение в `requirements.md`: не подменять ближайшим каноном без эталона).
2. Не выдумывать базовый цвет, если в тексте только marketing-name: извлекли `ржавая осень` → на сырое значение уверенность может быть высокой, на «оранжевый» — низкой/нулевой → `needs_review = true`.
3. UX: показать найденное в описании и отдельно поле «цвет для каталога» (выбор / правка селлера).
4. Долгосрочно: словарь marketing→facet в эталоне + feedback loop правок селлера в разметку; LLM только как кандидат, accept — после мэппинга на справочник.

**Формулировка для чекпоинта:** сохраняем «как бренд назвал»; в фильтр кладём канон только через справочник; иначе ручное уточнение — чтобы не ломать выдачу и не врать покупателю.

## 6. Что будет, если список обязательных полей изменится?

**Решение (продуктовая / системная политика):**

Обязательные поля — **не захардкожены в продукте**, а читаются из эталона категории в runtime (Stage 2 в `requirements.md` / `sequence.md`). Каталог и так меняется каждый день — это учтённый дрейф таксономии.

| Событие | Поведение |
| --- | --- |
| Добавили обязательный атрибут | На новых карточках сразу запрашиваем; нет в тексте → `value = null`, `needs_review` |
| Убрали атрибут | Больше не показываем как обязательный; судьба старых значений — политика каталога |
| Переименовали / сменили канон | Версия справочника + мэппинг на стороне каталога; сервис читает актуальную схему |
| Уже залитые карточки | MVP: дозаполнение при следующем редактировании; целевой: опциональный batch reprocess |

Закладываем:

- обязательность — свойство **версии схемы категории**;
- ответ API всегда «по текущему списку обязательных», часть может быть `null`;
- смена схемы не ломает контракт: UI рисует то, что пришло;
- мониторинг доли `null` по новым обязательным после смены схемы.

**Формулировка для чекпоинта:** список обязательных полей приходит из эталона на каждый запрос; продукт устойчив к эволюции каталога без переписывания пайплайна.
