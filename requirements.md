# Бизнес-требования

> MVP сервиса автозаполнения характеристик товаров для ЛК поставщика М.Видео.  
> Документ из двух частей: **(1) спецификация пайплайна** извлечения — как устроена «магия» между вводом и результатом — и **(2) требования пользователя** в формате user stories.

---

## Общие сведения

### Название

Автозаполнение характеристик карточки товара (извлечение атрибутов из текста).

### Суть

Селлер вводит название и описание → сервис извлекает обязательные атрибуты категории, приводит к канону каталога и возвращает `{атрибут, значение, уверенность}` → селлер проверяет сомнительные поля.

Встраивается в шаг онбординга **«Заведите карточки товаров»**.

### Пользователь

Селлер / поставщик М.Видео (менеджер по контенту). В **MVP авторизации нет**: прототип открывается без входа; в целевом продукте сценарий живёт внутри уже авторизованного ЛК.

### Ограничения кейса (обязательные)

| Ограничение | Смысл |
| --- | --- |
| Только текст | Название, описание, опционально сырые атрибуты продавца. **Изображения не используются** |
| Откуда берём значение | Только из текста этой карточки (название и описание). Не копируем характеристики с других товаров каталога |
| Эталон каталога | Обязательные поля категории + допустимые канонические значения |
| Без выдумок | Значение должно опираться на исходный текст |
| Гибрид по стоимости | Дешёвые методы первыми; ML/LLM — только на незакрытых полях |
| Справедливость | Не хуже обрабатывать редкие категории и небольших продавцов |

### UI MVP (кратко)

1. Ввод — «Введите название и описание товара»  
2. Ожидание — «Изучаю информацию и готовлю карточку»  
3. Результат — атрибут / значение / уверенность + правка  

Лимиты: название **300**, описание **6000** символов.  
Цвета: фон `#ffffff`, акцент `#ff0000`, «Атрибут уточнен» `#36a840`.

# Часть 1. Спецификация пайплайна извлечения

Формат: **Pipeline Stage Spec** — общепринятый способ описывать data/ML-пайплайны:  
**контракт I/O → схема стадий → карточка каждой стадии (вход / действие / выход / ограничения) → маршрутизация методов → качество и риски**.

Это не user stories: пользователь ждёт на экране ожидания, пока отрабатывают стадии ниже. UI-сценарий — в **части 2**.

---

## 1.1. Контракт сервиса

### Вход (от селлера / API)

| Поле | Тип | Обязательность | Лимит |
| --- | --- | --- | --- |
| `title` | string | да | ≤ 300 |
| `description` | string | да | ≤ 6000 |
| `seller_attrs` | map string→string | нет | — |

Изображения **не входят** во вход.

### Внутренний эталон (не ввод селлера)

- список обязательных атрибутов категории;
- допустимые / канонические значения атрибутов.

### Выход

Список по обязательным полям категории:

```text
{ attribute, value | null, confidence ∈ [0, 1], needs_review? }
```

Правила выхода:
- значения — в **каноне** справочника;
- нет значения в эталоне / нет опоры в тексте → `null` + проверка человеком;
- **нельзя** выдавать характеристику, которой нет в тексте карточки.

### Примеры обязательных полей

| Категория | Обязательные атрибуты |
| --- | --- |
| Смартфон | бренд, модель, объём памяти, диагональ экрана, ёмкость батареи, цвет |
| Ноутбук | бренд, процессор, объём ОЗУ, накопитель, диагональ, цвет |

Точный перечень фиксируется вместе с датасетом кейсодателя.

## 1.2. Схема пайплайна (end-to-end)

```text
Текст карточки
(title + description [+ seller_attrs])
        │
        ▼
┌───────────────────┐
│ 1. Препроцессинг  │
└─────────┬─────────┘
          ▼
┌───────────────────────────────────────────┐
│ 2. Категория → обязательные атрибуты      │
│    (эталон каталога)                      │
└─────────┬─────────────────────────────────┘
          ▼
┌───────────────────────────────────────────┐
│ 3. Извлечение значений из текста          │
│    (гибрид: правила → ML → LLM)           │
└─────────┬─────────────────────────────────┘
          ▼
┌───────────────────────────────────────────┐
│ 4. Нормализация + мэппинг на эталон       │
└─────────┬─────────────────────────────────┘
          ▼
┌───────────────────────────────────────────┐
│ 5. Уверенность + проверки                 │
│    (в т.ч. «значение есть в тексте»)      │
└─────────┬─────────────────────────────────┘
          ▼
┌───────────────────────────────────────────┐
│ 6. Показ селлеру                          │
│    (подсветка сомнительного)              │
└───────────────────────────────────────────┘
```

После шага 6 в целевом продукте возможна **петля улучшения** (не блокер MVP) — см. раздел в конце документа.

## 1.3. Стадии пайплайна

### Stage 1. Препроцессинг

| Параметр | Описание |
| --- | --- |
| Зачем | Убрать шум, не потеряв сигнал характеристик |
| Вход | Сырые `title`, `description`, `seller_attrs` |
| Делает | Очистка HTML, нормализация пробелов/юникода, склейка текста карточки |
| Выход | Очищенный текст для извлечения |
| Ограничения | Не вырезать числа, единицы, бренды, цвета |

---

### Stage 2. Категория → список обязательных атрибутов

| Параметр | Описание |
| --- | --- |
| Зачем | Знать, какие поля нужно заполнить |
| Вход | Очищенный текст |
| Делает | Определяет категорию; запрашивает у эталона обязательные атрибуты (+ допустимые значения) |
| Выход | `category` + список атрибутов-слотов под заполнение |
| Ограничения | Не заполняем поля от другой категории, если в тексте на это нет намёка. Для новых/редких категорий подключаем гибрид (правила → ML → LLM), см. 1.4 |

---

### Stage 3. Извлечение значений из текста

| Параметр | Описание |
| --- | --- |
| Зачем | Найти в тексте кандидатов значений для каждого обязательного атрибута |
| Вход | Текст + список атрибутов |
| Делает | Гибридное извлечение (1.4): сначала дёшево, дороже — только по незакрытым полям |
| Выход | Сырые кандидаты `{attribute → raw_value?}` |
| Ограничения | Источник — только текст карточки / seller_attrs; пустой слот допустим |

---

### Stage 4. Нормализация + мэппинг на эталон

| Параметр | Описание |
| --- | --- |
| Зачем | Привести к формату маркетплейса («алый» / «red» → канон; единицы → единый вид) |
| Вход | Сырые кандидаты + справочник допустимых значений |
| Делает | Нормализация написаний и единиц; сопоставление со справочником категории |
| Выход | Канонические значения или отказ мэппинга |
| Ограничения | Нет в эталоне → не выдавать как принятое; не подменять «ближайшим» каноном, если его нет в тексте |

---

### Stage 5. Уверенность + проверки

| Параметр | Описание |
| --- | --- |
| Зачем | Отделить надёжное от сомнительного; не пустить выдумки в каталог |
| Вход | Канонические кандидаты + исходный текст |
| Делает | Оценка `confidence`; проверка опоры на текст; применение порогов шкалы → `needs_review` |
| Выход | Финальный набор `{attribute, value, confidence, needs_review}` |
| Ограничения | При LLM — схема вывода, справочник, проверка «значение есть в тексте»; пороги — см. ниже |

#### Шкала уверенности (продуктовое решение команды)

Заказчик требует оценку уверенности и порог для ручной проверки, но **не задаёт числовую шкалу**. Ниже — пороги MVP (согласованы с прототипом).

`confidence` — число от **0** до **1** (в UI можно показывать как `0,98`).

| Уровень | Условие | `needs_review` | Поведение в UI / каталоге |
| --- | --- | --- | --- |
| Нет значения | `value` пустой / null (в т.ч. отказ мэппинга) | да | Плейсхолдер «не найдено — заполните вручную», подсветка сомнительного; в каталог не принимать автоматически |
| Низкая уверенность | `0 ≤ confidence < 0,85` | да | Подсветка сомнительного; селлер должен проверить / править; в целевом продукте — кандидат в очередь разметки |
| Высокая уверенность | `confidence ≥ 0,85` | нет | Обычное отображение (число + шкала без предупреждающей подсветки); можно считать принятым, пока селлер не правил |

Дополнительно:
- если значение **не опирается на текст** карточки (выдумка) — не выдаём как принятое: `value = null`, `confidence = 0`, `needs_review = да`;
- после ручного уточнения селлером вместо шкалы показываем «Атрибут уточнен» (поле снято с сомнительных);
- порог **0,85** можно пересмотреть после калибровки на gold-сете (не меняет контракт полей ответа).

---

### Stage 6. Показ селлеру

| Параметр | Описание |
| --- | --- |
| Зачем | Человек подтверждает сомнительное до попадания в каталог |
| Вход | Результат Stage 5 |
| Делает | Рендер UI (часть 2): шкала уверенности, подсветка, правка «Атрибут уточнен» |
| Выход | Карточка, готовая к продолжению онбординга / сохранению (в проде) |
| Ограничения | MVP не пишет в боевой каталог; правка локальна на экране |

## 1.4. Гибридная маршрутизация методов (внутри Stage 3)

Компромисс **покрытие ↔ стоимость ↔ cold-start**. Подходы сосуществуют, а не заменяют друг друга.

| Слой | Метод | Когда | Стоимость | Сильная сторона |
| --- | --- | --- | --- | --- |
| 1 | Правила и словари (regex, бренд-листы, цвета, единицы) | Всегда первым | Очень низкая | Ядро, прозрачность, базлайн |
| 2 | ML / NER (sequence labeling, при необходимости энкодер) | Только незакрытые после слоя 1 | Средняя | Свободные формулировки |
| 3 | LLM (few-shot + JSON-схема) | Только незакрытые после слоя 2 / cold-start | Высокая | Новые категории, хвост |

**Правило роутера:** не вызывать LLM «на всю карточку целиком», а точечно — по полям, где без него не обойтись.

---

## 1.5. Петля обратной связи (целевой контур)

Кратко: ошибки и low-confidence после показа селлеру → разметка → обновление правил/модели → лучше работают стадии 3–5.  
Подробно — в разделе **«Целевой контур улучшения»** в конце документа. В прототипе достаточно правки селлером в UI (US-1.3.3).

## 1.6. Метрики успеха пайплайна

Общая accuracy (доля верных ответов «в среднем по всему») **не подходит** — она маскирует провалы на редких значениях.  
Считаем **по каждому атрибуту** на gold-сете (эталонной выборке, размеченной людьми).  
Цифры ниже — **ориентиры пилота** (целевые пороги до/после первого прогона на разметке кейсодателя).

**Голова** — частые, типовые случаи (популярные категории и значения, много примеров в данных).  
**Хвост** — редкие категории и редкие значения, примеров мало.

| Метрика | Смысл | Ориентир пилота |
| --- | --- | --- |
| Precision (точность) по атрибуту | Из предложенных значений какая доля верна | ≥ 0,90–0,95 на голове (например бренд, память); ≥ 0,85 на хвосте (например цвет, редкие значения) |
| Recall (полнота) по атрибуту | Из значений, которые есть в тексте/разметке, какую долю нашли | ≥ 0,80–0,90 на голове; ≥ 0,70 на хвосте |
| F1 (баланс точности и полноты) по атрибуту | Сводная оценка качества по полю | ≥ 0,85–0,92 на атрибутах, по которым чаще всего фильтруют в поиске |
| Coverage (покрытие) | Доля карточек, где атрибут заполнен (не пустой) | на 15–30 процентных пунктов выше, чем без помощника |
| Доля «выдуманных» атрибутов | Предложили значение, которого нет в тексте / сырых атрибутах продавца | **менее 2%** — жёсткий порог |
| Взвешивание по трафику | Ошибки и F1 считают с большим весом для атрибутов, по которым покупатели реально фильтруют | Качество самых важных для фильтров атрибутов не хуже, чем на типовых случаях |
| Оценка на gold по категориям | Отдельно смотрим частые и редкие категории на эталонной выборке | На редких категориях F1 (баланс точности и полноты) падает относительно частых не больше чем на 10–15 процентных пунктов |

---

## 1.7. Риски пайплайна и меры

| Риск | Последствие | Мера |
| --- | --- | --- |
| Галлюцинации LLM | Ложные атрибуты ломают фильтры | Schema + эталон + проверка «есть в тексте» + порог |
| Стоимость на масштабе | LLM дорого на каждый SKU | Гибридный роутер, кэш, дистилляция |
| Eval не покрывает хвост | Метрика красивая, качество плохое | Gold-сеты по редким категориям |
| Дрейф новых категорий | Падение качества со временем | Мониторинг + петля разметки |
| Несправедливость к мелким продавцам | Хвост ассортимента хуже | Контроль покрытия по сегментам |
| Эталон не подключён в раннем прототипе | Канон «из кода», не из справочника | Техдолг: подключить справочник/разметку датасета на этапе разработки |

# Часть 2. Требования пользователя (User Stories)

## Условные обозначения

Стори: **Как… я хочу… чтобы…** + критерии приёмки.

Только то, что видит и делает селлер. Техническая обработка описана в **части 1**.

## Раздел 1. Создание карточки

**Роль:** селлер.  
**Предусловие MVP:** авторизация не требуется.

---

### Эпик 1.1 Ввод данных

#### US-1.1.1. Открыть экран ввода без входа


**Как** селлер,  
**я хочу** открыть создание карточки без регистрации и логина,  
**чтобы** сразу ввести название и описание.

**Критерии приёмки:**
1. Открывается экран с заголовком «Введите название и описание товара».
2. Нет экранов auth / регистрации.
3. Доступны поля «Название», «Описание» и действие запуска.

---

#### US-1.1.2. Ввести название


**Как** селлер,  
**я хочу** ввести название товара (до 300 символов),  
**чтобы** сервис использовал его как источник характеристик.

**Критерии приёмки:**
1. Поле «Название» обязательное.
2. Под полем счётчик `N / 300`.
3. Ввод сверх лимита невозможен.

---

#### US-1.1.3. Ввести описание


**Как** селлер,  
**я хочу** ввести описание товара (до 6000 символов),  
**чтобы** извлечь характеристики из свободного текста.

**Критерии приёмки:**
1. Многострочное поле «Описание».
2. Поле «Описание» обязательное.
3. Под полем счётчик `N / 6000`.
4. Ввод сверх лимита невозможен.
5. Без заполненного описания запуск подготовки карточки не выполняется.

---

#### US-1.1.4. Запустить подготовку карточки


**Как** селлер,  
**я хочу** нажать «Подготовить карточку»,  
**чтобы** получить заполненные атрибуты.

**Критерии приёмки:**
1. Кнопка справа внизу экрана ввода.
2. Без названия или описания запуск не выполняется.
3. После запуска — экран ожидания.
4. В MVP есть демо-примеры (смартфон / ноутбук / слабое описание).

---

### Эпик 1.2 Ожидание

#### US-1.2.1. Видеть статус обработки


**Как** селлер,  
**я хочу** видеть, что карточка готовится,  
**чтобы** понимать, что нужно подождать.

**Критерии приёмки:**
1. Текст «Изучаю информацию и готовлю карточку» + анимация.
2. Подсказка статуса по центру под заголовком.
3. На этом экране поля не редактируются.

---

### Эпик 1.3 Результат и правка

#### US-1.3.1. Увидеть атрибуты с уверенностью


**Как** селлер,  
**я хочу** увидеть заголовок, описание и ключевые атрибуты категории,  
**чтобы** проверить карточку перед продолжением.

**Критерии приёмки:**
1. Блок «Ключевые атрибуты»: атрибут / значение / уверенность (число + шкала).
2. Есть подсказка проверить поля с низкой уверенностью.
3. Обязательные поля категории показаны даже если значение не найдено.

---

#### US-1.3.2. Увидеть сомнительные поля


**Как** селлер,  
**я хочу** видеть подсветку низкой уверенности и пустых значений,  
**чтобы** исправить их вручную.

**Критерии приёмки:**
1. Поля с `confidence < 0,85` или без значения визуально отличаются (подсветка сомнительного).
2. Поля с `confidence ≥ 0,85` и непустым значением показываются без предупреждающей подсветки.
3. Для пустого значения — понятный плейсхолдер («не найдено — заполните вручную»).

---

#### US-1.3.3. Править один атрибут


**Как** селлер,  
**я хочу** нажать «Править» у конкретного поля и сохранить значение,  
**чтобы** исправить ошибку без повторного запуска всего сценария.

**Критерии приёмки:**
1. У каждой строки — кнопка «Править».
2. В режиме правки — явная кнопка «Сохранить» (не «…»).
3. После сохранения вместо шкалы — «Атрибут уточнен» (`#36a840`).
4. Общей кнопки «Править сомнительные» нет.

---

#### US-1.3.4. Начать новую карточку


**Как** селлер,  
**я хочу** нажать «Новая карточка»,  
**чтобы** заполнить следующий товар.

**Критерии приёмки:**
1. Красная кнопка справа внизу экрана результата.
2. В правом верхнем углу такой кнопки нет.
3. Возврат на экран ввода.

# Целевой контур улучшения (после MVP)

Это **не шаг экрана** и не обязательная часть кликабельного прототипа.  
Это продакшен-петля: как система становится точнее со временем, после того как результат уже показали селлеру (шаг 6 пайплайна).

## Зачем

Автоизвлечение ошибается и сомневается. Если только править карточку «на месте» и не сохранять урок, одни и те же ошибки повторяются на следующих товарах. Петля превращает правки людей в улучшение правил и моделей.

## Как работает

```text
После шага 6 (показ селлеру)
        │
        ▼
Ошибка или low-confidence
(сервис ошибся / не уверен / значения нет)
        │
        ▼
Ручная разметка
(селлер в UI и/или модератор в очереди)
«правильное значение вот такое»
        │
        ▼
Обновление системы
• правила и словари
• дообучение ML
• правки промптов / схемы LLM
        │
        ▼
Следующие карточки проходят стадии 3–5 уже лучше
(извлечение → нормализация → уверенность)
```

Разбор по шагам:

1. **Триггер** — после показа результата поле с ошибкой, пустым значением или низкой уверенностью (low-confidence).
2. **Ручная разметка** — человек фиксирует верный канон. В MVP это правка селлера («Атрибут уточнен»). В целевом продукте спорные случаи могут уходить в очередь разметчиков каталога.
3. **Обновление правил / дообучение** — на размеченных примерах обновляют словари и regex, дообучают модель или усиливают контроль LLM.
4. **Эффект на стадиях 3–5** — улучшение действует на *новые* карточки: извлечение, мэппинг на эталон и оценка уверенности становятся точнее. Это не обязательный «пересчёт» той же карточки в том же сеансе.

## Что в MVP, что потом

| Сейчас (MVP) | Потом (целевой продукт) |
| --- | --- |
| Селлер правит поле в UI | + очередь модерации / разметки |
| Урок может не сохраняться в обучение | Правки логируются и идут в правила/модель |
| Достаточно для демо сценария | Плюс к приёмке кейса и устойчивости каталога |

## Связь с заданием

В задании М.Видео прямо указано: ошибки и случаи с низкой уверенностью уходят на ручную разметку и возвращаются в обучение или обновление правил. Если решение учитывает такую петлю — это плюс на защите.
